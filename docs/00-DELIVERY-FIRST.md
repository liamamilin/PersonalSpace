# 00 · 能力优先：Codex 首先要理解的开发策略

> **交付的是能使用的能力，而不是为了未来可能性设计的体系。**

## 1. 每次交付都从用户动作出发

编码前写出一句可实际操作的目标，例如：

- 「我选了 Downloads 和 Documents，搜一个文件名，能预览并在 Finder 中打开原件。」
- 「我创建‘我的电脑’，把订单和保修凭证关联起来，重启后关系仍在。」
- 「我识别一张订单，确认日期，收到提醒，点击后返回凭证。」

然后只开发完成这条路径所需的界面、数据与逻辑。完成后再做下一条；不要先建未来六个月可能用到的底座。

## 2. 做加法需要证据，做减法不需要论证

| 优先做 | 暂时不要做 | 何时再考虑 |
|---|---|---|
| 文件夹授权 + 扫描 + 搜索 | 守护进程、FSEvents 增量引擎、通用文件身份图 | 手动刷新/启动补扫已无法满足实测使用 |
| 单一 SQLite/GRDB 数据层 | Repository/Service/UseCase 各一套抽象和事件总线 | 有两个真实调用方、第二种具体实现或测试痛点 |
| 一个 Item 指向一份来源文件 | 多文件位置归并、跨卷重命名跟踪、内容寻址存储 | 用户确实需要合并重复文件 |
| 用户操作时 OCR + 可编辑候选 | 默认批量 OCR 整个硬盘、智能工作流 | 有可靠的主流程、明确的用户收益 |
| Action 保存后调度本地通知 | 分布式事务、通知状态协调器、多层重试队列 | 发现可复现的不一致后做最小修复 |
| 托管复制 + 一次校验 | 自动去重、定期全盘哈希、孤儿扫描任务 | 有可测的数据问题或真实容量压力 |
| 固定几类事务 | 业务 DSL、通用规则引擎、插件系统 | 四类事务已证明共享规则不足 |

**不要把表中“暂时不要做”理解成永远禁止。** 只有当当前实现出现明确缺陷，且简单修复不足时，再选最小复杂度的扩展。不要因为“以后可能用到”就提前开发。

## 3. 什么是必须保留的底线

这四类问题不能靠后期 UI 打磨补救：

1. **用户文件不能被误删或误改**：扫描只读；托管仅复制；不提供删除源文件功能。
2. **不能越权读取**：只访问用户选定的目录和 PhotoKit 授权的照片。
3. **不能传播秘密**：疑似密码的正文不进入普通全文搜索、模型输入、日志或通知。
4. **不能制造错误提醒**：文档缺失日期就提示补充；AI 的日期是候选，确认后才调度。

此外，存储和提醒等操作**不能假装成功**：数据库写入/文件复制/系统通知安排不成功，就不能展示成功反馈。

这就是防护的主体。正常的失败应有可理解的提示与重试入口，但**不必为每个假设性失败写复杂恢复状态机**。

## 4. 推荐实现方式

- 先写真实业务代码，再在重复逻辑出现时提取共用函数。
- 一个数据库、一套真正的数据模型、一个原生应用进程；模块按已实现功能拆分，不建空模块。
- 先跑通一份数据的流程，再做批量和性能优化。
- 优先采用系统控件：`NavigationSplitView`、`Table`、`NSOpenPanel`、Quick Look、PDFKit、Vision、UserNotifications。
- 任何“通用基础设施”都应能回答：**当前哪个用户场景没有它就做不成？** 答不上来就先不建。
- 遇到 bug 找根因并改正，不连续叠包装层、重试层、拦截层和补丁。

## 5. 交付方式（避免过度审查）

每轮最多回答四件事：

1. **做成了什么**：可操作的功能、代码路径。
2. **怎么操作**：2–5 分钟完整演示路径。
3. **真实验证**：构建/测试结果、必要截图、未通过项。
4. **下一步**：只建议一个紧邻能力。

不要创建独立的评审 Agent、门禁评分系统、风险看板或每日状态报告。必要的测试是为了确保能力真实有效，不是另一项产品。

## 6. “专业”的定义

专业不是页面多、抽象多、动画多，而是用户打开应用后，能立即看出在哪里添加资料，能高效查找、预览、归档和关联；控件符合 macOS 行为、响应稳定、文案准确，且真实数据不会丢。设计工作与功能实现同步，**不是完成所有业务后才换皮**。
