# 04 · 实用技术架构：一个原生应用，少量明确组件

## 1. 选型（不再讨论技术大选）

| 需求 | 方案 | 为什么 |
|---|---|---|
| 原生 macOS | Swift 6 + SwiftUI，必要时 AppKit | 系统窗口、Table、菜单、键盘、Finder/Quick Look |
| 目标系统 | macOS 26+ | 为可选 Apple Foundation Models 预留环境；具体 API 以本机 SDK 为准 |
| 本地结构化数据 | SQLite + GRDB | 一个数据库管理文件索引与对象/事务关系；后期可增加 FTS5 |
| 目录权限 | NSOpenPanel + security-scoped bookmark | 用户明确授权；重启后访问已选目录 |
| 扫描文件 | FileManager | 初扫、手动刷新、重新启动后补扫即可支撑 M1 |
| 文件打开和预览 | NSWorkspace + Quick Look / PDFKit | 少写自定义解码代码 |
| 归档副本 | FileManager + CryptoKit | 用户主动复制、一次校验、持久保存 |
| 订单文字 | PDFKit + Vision | 本地提取，不依赖网络 |
| AI 字段建议 | Apple Foundation Models（可选） | 可用时减轻录入；不可用时人工操作 |
| 到期提醒 | UserNotifications | 系统本地提醒，无需常驻后台进程 |
| Photos | PhotoKit（M5） | 正规只读访问，不能遍历照片库包 |

默认只运行一个 App 进程、一个权威数据库。不需要 Python、Docker、服务器、插件系统或登录项。

## 2. 工程目录按实现逐步生长

M1 先有这些代码即可（名称可按实际项目调整）：

```text
PersonalSpace/
├── PersonalSpace.xcodeproj
├── App/
│   ├── PersonalSpaceApp.swift
│   └── AppCommands.swift
├── Library/
│   ├── LibraryView.swift
│   ├── FileDetailView.swift
│   ├── FolderScanner.swift
│   └── FolderAccess.swift
├── Settings/
│   └── SourcesView.swift
├── Data/
│   ├── Database.swift
│   └── Records.swift
└── Tests/
```

M2 时再加 `Objects/`、`ManagedFiles/`，M3 加 `Matters/`、`Reminders/`，M5 才加 `Photos/`。**不创建空的 Features/Domain/Infrastructure/Repository/UseCase 五层树。**

分工只需清晰：UI 不自己扫描文件；Scanner 不修改 UI；SQLite 数据访问集中；系统通知代码集中。若某个功能简单，用一个具体类型即可，不强制每个类先定义 protocol。

## 3. M1 的最短真实数据流

```text
用户点「添加文件夹」
  → NSOpenPanel 选择目录
  → 保存 bookmark（Source）
  → FolderScanner 后台枚举文件
  → 每批写入 SQLite（Item）
  → Table 查询并展示真实文件
  → 搜索/选择 → 预览 / Finder 定位
```

### 目录授权

- App Sandbox 开启，只申请用户选择目录需要的访问能力。
- 用户通过 NSOpenPanel 选择文件夹，持久保存安全作用域 bookmark；重启解析和开启访问，完成文件操作后释放授权。
- 书签失效时保留已索引列表，显示「重新授权」。不要默认请求 Full Disk Access。
- 跳过目录包和符号链接，不递归进入应用包、Photos Library 内部。

这四点已足够构成可靠的 M1 授权行为。不要先做一个适配十种来源的通用安全权限框架。

### 扫描

- 初次扫描使用 `FileManager.enumerator`，逐项取文件名、大小、UTType、修改日期、相对路径；按小批次写数据库。
- 后台执行，不阻塞 SwiftUI 主线程；显示真实已发现数量，支持用户手动刷新。
- 用户重新启动时可以对已授权来源重新扫一遍；先保证结果一致。**FSEvents 不是 M1 的要求**，只有真实扫描耗时或用户反馈要求持续更新时才引入。
- 初期用 `source_id + relative_path` 识别一个条目，不合并同内容文件。文件重命名后，旧路径可被标为失效、新路径作为新记录；先不实现跨卷追踪。
- 仅在一次扫描**成功结束**后，才能将这次未再发现的旧记录标记不可用；取消/失败不能把旧文件批量标成丢失。
- 不在扫描过程中默认 OCR 所有文档，不计算所有文件哈希，不预加载视频/图片正文。

**为什么这样实现**：这是普通用户可以稳定使用的真实基础。等“一个目录 10k 文件扫描实际太慢”时，再根据 Instruments 和数据决定哪些索引/并发/增量机制值得上。

### 查询与预览

- 文件名/来源/相对路径用 SQLite 查询；列表结果分批加载或使用适合的惰性数据源，不把整个磁盘内容一次变成大量 SwiftUI View。
- 文件存在且有权限时通过系统能力打开和定位；Quick Look 集成以真实运行行为为准，优先减少自绘预览。
- 文件缺失时用户仍可看到文件名和原位置；移除/重新授权来源后可重新扫描。

## 4. M2：对象与归档（复制，不迁移）

### 个人对象

- `personal_object` 与 `object_item` 两张表足够；一个对象关联多份 Item，一个 Item 可关联多个 Object。
- 关联/解绑是数据库操作，不移动文件，不更改用户文件夹。

### 归档副本

- 用户明确点击「保存副本到资料库」。
- 复制到 Application Support 内部目录，先写临时文件、计算一次 SHA-256 验证、再提交记录；不能在文件尚未完成复制时显示“归档完成”。
- Item 直接保存一个可选 `managed_copy_path` / `managed_sha256`；**无需提前建内容寻址 blob 库、重复文件协调器或垃圾回收服务**。
- 原路径仍在；若源路径不可用但托管副本存在，详情仍能打开副本。
- V1 不提供自动删除托管原件。清理数据可以之后在“数据管理”做受控用户操作。

## 5. M3：订单 → 事实 → 行动

```text
订单文件
  → PDFKit 文本 / Vision OCR（用户点击后进行）
  → 结构化字段建议（可选模型/轻量规则）
  → 用户直接在表单里修正并确认
  → 创建 Matter + Fact + Action
  → UserNotifications 安排提醒
  → 事务详情能打开原件
```

### 文档处理

1. 可读文本 PDF 优先 PDFKit；图片使用 Vision；扫描版 PDF 按需渲染单页后 OCR。
2. OCR 获取原文后允许用户查看；不把全文永久写进任何日志。
3. 可选 Foundation Models 生成字段候选。运行时检查可用性。模型不可用时保留用户可直接编辑的表单；不要为模型错误建立复杂重试机。
4. 关键日期、金额是**候选值**，默认需用户确认；事实保留来源 Item 和必要的原文片段。
5. 只处理用户选中的文档，不默认让后台模型扫描所有私人文件。

### 通知

- `Action` 保存一个已确认的具体提醒日期/时间，使用 Action UUID 派生稳定的通知 ID。
- 创建：请求或检查通知权限 → 安排通知 → 反馈真实状态。
- 编辑：先移除这个 Action 的旧 pending 请求，再提交新请求；完成/取消：移除 pending 请求。
- App 启动时可以对已保存的未来提醒做一次简短核对。**先不要创建 notification_record 表、通知状态协调器、事件溯源或重试队列**；出现可复现问题再补最小逻辑。
- 通知权限拒绝：Action 可以保存，但必须告知用户没有系统通知。

日期未知就不调度；不能把「购买日期」当成「退货截止日期」。

## 6. M4：扩展四类事务与全文查找

四类事务继续使用同一 Matter/Fact/Action：

| 事务 | 典型字段 | 典型行动 |
|---|---|---|
| 订单 | 商品、购买日期、商家、金额 | 退货/售后检查 |
| 保修 | 对应产品、保修期限、凭证 | 保修前检查 |
| 合同 | 合同双方、生效/终止日期、通知条款 | 续签前核对 |
| 订阅 | 服务、计费周期、下次扣费日 | 扣费前检查 |

需要差异化字段时用配置或很小的分支，不要建通用规则 DSL。

FTS5 在 M4 加入普通非敏感文档的可用文本；只有用户选择识别、或明确允许的类型才入正文索引。中文分词从实际测试结果选择简单的标题 `LIKE` fallback，不先自建搜索服务。SQLite + GRDB 仍是唯一数据库。

## 7. M5：PhotoKit / 敏感资料

- Photos 必须经用户同意，通过 PhotoKit 读取受允许的照片和小缩略图；按需获取，避免一口气同步几万张大图。
- 照片作为 Item 关联个人对象，使用 PhotoKit asset identifier，处理用户撤回权限导致的不可用状态即可；不遍历 `.photoslibrary` 内部路径。
- 文件名/类型表明疑似包含密码或恢复码时，标记为敏感候选，禁止默认 OCR/普通正文 FTS。用户可以手动标记敏感；不访问 Apple Passwords 或其它 App 的 Keychain。

## 8. M6：备份、可靠性和发布

- 应用存储两类重要数据：SQLite + 用户明确托管的文件副本。备份必须包含两者。
- SQLite 在 WAL 写入时要通过一致性快照机制导出，而不是仅复制单个 `.sqlite` 文件；生成包含版本、文件列表、哈希的 manifest。
- 恢复先对**新测试位置**完整验证，再替换当前库；失败不得破坏原有数据。
- 只索引的外部文件**不包含在备份中**，UI 要说清楚；恢复后可能需要用户重新授权来源目录。
- 对 10k 文件规模做一次实测，有问题才针对 SQL 查询、批量写入、视图加载做性能优化。
- 签名/公证仅在具备开发者证书的 Mac 上执行；没有证书则交付已验证的本机构建，不假称已发布。

## 9. 什么时候允许复杂化？

在变更里写出三句话就够了：

1. 哪个**已存在功能**在什么数据/动作下出现了可复现问题？
2. 简单修复为什么解决不了？
3. 引入这个结构后，用户可以完成原来做不到的什么？

如果无法回答，不引入新的抽象层或后台机制。
