# 08 · 质量与验收：少而关键，按里程碑执行

验收聚焦真实用户操作，不用“高测试数量”“所有状态机覆盖”替代可用软件。测试用合成文件和专用目录，绝不删除真实个人资料。

## 1. 编译与实际运行

在拥有 Xcode 的 Mac 上，确认 scheme 后执行：

```bash
xcodebuild -list -project PersonalSpace.xcodeproj
xcodebuild -project PersonalSpace.xcodeproj \
  -scheme PersonalSpace -configuration Debug \
  -destination 'platform=macOS' build
xcodebuild -project PersonalSpace.xcodeproj \
  -scheme PersonalSpace -configuration Debug \
  -destination 'platform=macOS' test
```

如果环境没有 Xcode、真实桌面、Photos 权限或开发者证书，诚实标记相应部分未验证；不合成所谓实际运行截图。

## 2. 各阶段的核心验收场景

| ID | 阶段 | 实际用户操作 | 应看到的结果 |

| A04 | M1 | 移动测试源文件后刷新 | 该条目显示不可用，不闪退或误删其它记录 |

| A06 | M2 | 创建对象并关联两份文件 | 关系保存，重启后仍在 |
| A07 | M2 | 托管复制后删除测试原件 | 校验通过，托管副本仍能打开 |

## 3. 哪些问题立即修，哪些以后再做

### 当前必须解决（阻断阶段交付）

- 关键用户路径无法完成、真实文件打不开、来源授权重启丢失。
- 扫描改变/删除用户原件、读入未经授权路径。
- 数据保存失败却提示成功，或阶段相关资料重启后丢失。
- 明文秘密进入普通全文索引或日志。
- AI 在无依据情况下自动确认日期并排期。
- 修改提醒却留下旧的待处理系统通知。

### 允许记录后继续下一阶段

- 未实现的后期能力（**不要显示假的可用入口**）。
- 未观察到的极端场景、未来扩展接口、尚未必要的跨卷重命名追踪。
- 微小图标/间距差异、尚未成为可复现问题的性能猜测。
- 暂无第二个实现的协议抽象、额外监控仪表盘和内部可观测性面板。

发布 V1 前仍应修好实际影响用户的已知错误，不是允许质量长期失控。

## 4. 专业视觉验收（具体而非形容词）

M1 实机截图至少两张：首次无资料，和真实文件列表+选中详情。优先看：

- 窗口是不是系统原生标题栏/Toolbar/三栏；有没有奇怪的大圆角网页卡片？
- 文件名、类型、来源、日期是否一眼能扫读；列表行是否过高？
- 主操作是否明确；“打开原件 / 在 Finder 中显示”是否真的有动作？
- 右侧预览是否是实际文件、空状态是否不展示虚构个人数据？
- 缩小窗口是否仍能操作；键盘 `⌘F`、`Space` 是否正常？

M6 再补全深浅色、高对比度、VoiceOver、较小窗口、长文件名、国际化日期/金额格式等检查；其中一旦在早期暴露明显不可用问题，也应当场修正。

## 5. 性能：先测再优化

- M1 先在真实几十/几百个文件的目录验证扫描不阻塞 UI，用户可以边扫描边浏览已发现内容。
- M6 用大约 10k 小文件、少量大文件测扫描、搜索、内存和滚动，报告实测环境和数值。
- 只有有证据的瓶颈才引入文件系统事件监控、查询优化、缓存、并发限流。不要为了假想的百万文件先实现复杂索引引擎。
