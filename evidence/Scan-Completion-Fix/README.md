# 可读范围扫描结束与按路径更新 · 0.10.5 (18)

## 完成能力

0.10.4 只解决自身写入触发重扫及停止失效，没有完成整个用户目录的扫描。后续使用原应用标识、相同沙盒权限和已有只读书签做限时元数据诊断，确认系统拒绝读取多处通讯录、短信、日历等受保护目录；没有读取文件正文、修改原件或扩大权限。根目录列举和原书签解析正常，书签未过期。

扫描现在区分根目录/数据库等致命失败与子目录无法读取：遍历结束后保存真实结束时间和未读取位置。未读取子树的历史记录、对象/事务关联保留，原件访问问题单独标注，旧正文不用于全文命中；普通可读资料继续正常工作。文件在扫描时消失按实际不可用处理，停止或根目录失效不宣称扫描完成。

FSEvents 保留变化路径，普通变化只处理对应文件或子目录；事件丢失、根目录变化等情况完整补扫。完整遍历和局部更新分别显示，后续局部更新保留上次完整遍历时间。数据库写入失败不再错误地显示为重新授权，安全错误类别保存在应用自己的诊断目录，不记录正文或 SQL 参数。

## 用户操作路径

已更新到用户原安装位置的 0.10.5，原 0.10.4 程序本机保留可回退。来源页点击恢复自动更新后，实际用户来源在 2026-11-07 16:15（Asia/Shanghai）遍历结束，登记 1,788,020 个可读文件，显示 143 个未能读取位置及可展开清单。自动更新保持开启，扫描进度与停止按钮消失。

后续真实界面出现「更新中 · 已处理 166 个文件」，完整遍历结束时间与数量保持不变；再核对时已恢复空闲，资料记录从 1,790,303 增到 1,790,771，说明变化按局部处理，没有因新文件再次启动整轮遍历。资料记录包含历史路径，不能等同于本轮可读文件数量。

一次早期实际试跑曾中断；该阶段还有外部 SQLite 观察，之后停止外部数据库读取，仅使用原生界面与进程采样核验。最终以上述真实结束状态为准。搜索窗口的额外 GUI 验证发生自动化超时，没有把该项写成通过；已返回来源页并再次核对结束时间和自动更新状态。

### 开源实现对照

用户要求参考开源项目后，已阅读下列实际实现，未运行其代码，也未把第三方项目替换为应用依赖：

- [Oil Find / Scanner.swift](https://github.com/oil-oil/oil-find/blob/main/Sources/OilFindCore/Scanner.swift)：目录句柄、`O_NOFOLLOW`、文件标识校验、批量元数据读取和无权访问范围记录；[FSWatcher.swift](https://github.com/oil-oil/oil-find/blob/main/Sources/OilFindCore/FSWatcher.swift) 保留事件路径及序号，区分正常变化和需要补扫的事件。
- [EverythingMac / fswalk](https://github.com/seedds/EverythingMac/blob/main/engine/fswalk/src/lib.rs)：不跟随符号链接、权限失败时保留对应节点、可取消遍历与按需获取元数据。
- [Syncthing / scanner/walk.go](https://github.com/syncthing/syncthing/blob/main/lib/scanner/walk.go)：具体路径错误与扫描结果分开处理；当前文件与已有元数据比较，未变化时跳过后续处理。
- [FSearch / database_scan.c](https://github.com/cboxdoerfer/fsearch/blob/master/src/fsearch_database_scan.c) 与 [database_index.c](https://github.com/cboxdoerfer/fsearch/blob/master/src/fsearch_database_index.c)：首次目录遍历、可取消处理与后续事件更新分开。

本机三秒进程采样显示，扫描 worker 多次等待数据库队列；该队列大量堆栈处在 `LibraryModel.reload()` 的待整理计数查询，同时也能看到目录枚举预取文件类型的开销。对隔离内存库的 500,000 条合成记录进行五次计数，中位数从约 10.58 毫秒降到约 0.0012 毫秒，查询计划由全表扫描变成 `kind` 索引查询。这只证明该查询的优化方向，不是应用整体或磁盘扫描速度测试；正在运行的用户资料库没有被这项实验修改。

原始源码版本、下载文件、采样和隔离测试数据保留本机 `references/`、`live-scan-sample.txt`、`inbox-count-benchmark.json`，均位于 `.build/Scan-Completion-Fix/`。后续性能改进应优先消除重复全表计数和不必要的逐文件元数据工作，再根据实测决定是否采用更底层的目录读取方式。

另做 20,000 个合成文件的轻量元数据枚举比较：原方式约 0.175 秒、峰值 RSS 13.1 MB；扩展名类型缓存与逐条 autoreleasepool 组合约 0.145 秒、12.8 MB。该样例没有复现真实扫描 5.2 GB 的峰值，不能据此宣称内存问题已解决，亦未将这项组合改动合入运行版。首次在受限执行沙盒中运行该样例失败，允许系统元数据服务后两种方式均读取相同的 20,000 个文件。
