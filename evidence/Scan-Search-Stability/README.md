# 持续更新期间的搜索与扫描稳定性 · 0.10.7 (22)

## 完成能力

用户反馈长期忙碌及「所有资料」空结果后，确认 0.10.6 的进度刷新保护没有覆盖局部更新完成时的刷新。旧逻辑为每次请求递增查询代数，持续变化可作废正在执行的相同条件查询，并把查询尚未完成显示成空结果。新增隔离回归在旧代码得到 31 次搜索读取，超过最多两次的要求，测试明确失败。

刷新现在共享一个异步读取，通过请求序号确保调用者得到其请求后的读取，不因后续同条件请求丢弃当前结果；条件变化时不展示旧条件的结果，取消某个窗口任务不取消共享读取。界面以实际完成的查询条件区分「正在查询」、读取失败及真实零结果。

文件级通知中，目录仅有内容时间或扩展属性变化时不递归遍历全部子文件；实际文件事件继续处理。目录结构、权限和 FinderInfo 可见性变化保留核对。MustScanSubDirs 单独出现时核对对应子树；根变化、事件丢失等情况保守地核对完整来源。依据本机 SDK FSEvents.h 的事件语义，不把事件流当作文件系统事实日志。

对元数据、可用性及访问状态均未变的文件，批量只更新 scanID；不重新生成冲突时无用的 UUID，也不改写全部元数据和二级索引。原有索引时间、显式正文、敏感标记和关联保留。真实变化、不可用后恢复或访问错误恢复仍走完整更新与正文新鲜度逻辑。没有移动或删除用户原件，没有新增服务或引擎层次。

## 用户操作路径

当前用户手动暂停了 milin 来源，不能将这个空闲状态计为问题已解决。新版本准备使用同一 AI Desktop Assistant 证书替换安装；先核对所有资料与查询状态，再进行真实来源的持续变化、查询与收尾验收。实机验证尚在进行，不把隔离测试当成真实目录验收。

## 构建/测试证据

- 旧逻辑：并发 31 次刷新实际执行 31 次搜索读取，回归失败。修复后同一回归通过，并验证取消旧任务及切换关键词不发布旧结果。
- 100 次持续刷新，模拟单次搜索读取 120 毫秒：刷新流仍在产生请求时，700 毫秒内已发布正确结果。该测试针对查询活性，未宣称 GUI 实际查询延迟为 120 或 700 毫秒。
- 最终 107 项 XCTest 全量通过，涵盖真实 FSEvents、权限及历史资料保留、正文新鲜度、目录事件范围、查询合并和不变文件索引时间保留。早期新增测试曾因返回非 Sendable 的 GRDB Row 编译失败，改为返回值元组后重新全量通过。
- 50,000 个相同合成文件，两份相同起始索引，独立进程交替三轮重扫：旧版 5.053 / 4.376 / 4.460 秒，新版 3.122 / 3.136 / 3.132 秒，中位数约减少 30%。每轮数量一致，无读取错误；不包含 GUI 和生产资料，不外推到百万文件目录。

完整日志、xcresult、合成基准和安装记录保留本机 `.build/Scan-Search-Stability/`。版本继续使用既有本机证书和 App Sandbox，不修改系统权限或读取应用数据目录来做外部核对。
